# Audit checkpoint — 2026-08-24

## LXToolPi state

The repository was dirty before this work. Existing modified files and the
untracked Pi AES67 implementation were preserved. The Mac project was created
only under `macos/AESBridge`.

The current Pi implementation delegates media transport and timing to
PipeWire and linuxptp. `app/audio/aes67.py` observes the PipeWire graph and
links eight hardware ports in an explicit ALSA order. Its templates configure
S24BE/48 kHz/8 channels, one-millisecond RTP, SAP and PTP domain 0. The current
defaults are recorded in the project README.

Items to verify on the physical Pi:

1. The exact ALSA card name/profile for RASPIAUDIO 8xIN+8xOUT; the code currently
   matches `hifiberry`.
2. Whether the selected Pi Ethernet controller exposes a stable PHC on the
   installed kernel. The installer falls back to software timestamps.
3. The SDP generated by the installed PipeWire version, especially payload
   type, `ts-refclk`, `mediaclk`, channel count and source filter.
4. Whether `239.255.255.255` SAP announcements are visible on the Mac's chosen
   Ethernet interface.
5. Eight PipeWire links in each direction and exact physical channel order.

## Upstream AES67_macos_Driver

Audited repository: `maxajbarlow/AES67_macos_Driver`, commit
`a2bba6220a8c74880e2599bdc224e97ab54f7b0e`, dated 2026-04-09.

License result:

- The authoritative `LICENSE` is GNU GPL version 3.
- GitHub classifies the repository as GPL-3.0.
- The audited commit message changes the license to GPL-3.0.
- The README's final license section still says MIT and is stale.
- libASPL itself is MIT-licensed and compatible with this GPLv3 derivative.

Architectural findings:

- Good: user-space AudioServerPlugIn, libASPL, SPSC rings, preallocated callback
  buffers, interface-specific multicast support and useful synthetic tests.
- Rejected for LXTool: 128-channel and multi-rate generality, hard-coded test
  streams, network threads inside the HAL plug-in, and configuration file I/O
  initiated from the driver host.
- Risk: the upstream SAP listener is hard-coded to `224.2.127.254`, while the
  LXToolPi template uses `239.255.255.255`.
- Risk: the upstream RTP header uses C++ bitfields; wire layout is
  implementation-defined. LXTool serializes every RTP header byte explicitly.
- Risk: upstream PTP binds privileged UDP ports from the driver context and
  documents a silent local-clock fallback. That cannot be treated as PTP lock.
- Risk: several upstream jitter-buffer implementations use mutexes; only its
  lock-free path is acceptable, and no such object may be touched by the Core
  Audio callback unless its producer/consumer ownership is proven.
- Risk: TX, real grandmaster PTP, manager control, adverse jitter and long-term
  stability are explicitly unvalidated upstream.

No vendored ptpd code, prebuilt binaries, generated Makefiles or proprietary
Merging material were imported.

## Apple architecture constraints

Apple's AudioServerPlugIn sample installs a `.driver` bundle in
`/Library/Audio/Plug-Ins/HAL`. AudioServerPlugIns run in a restricted host;
cross-process communication requires an allowed Mach service declared in
`AudioServerPlugIn_MachServices`. The AES Bridge plist declares
`org.maxpierr.aesbridge.engine` for the planned service boundary.

The final separation is:

```text
Core Audio apps
    ↕ float32 interleaved, 8×8/48 kHz
AudioServerPlugIn (no locks/network/allocation in callback)
    ↕ preallocated shared-memory SPSC rings + atomic status page
privileged launchd engine / Mach service
    ↕ RTP L24 + SAP/SDP + PTPv2 on selected Ethernet interface
LXToolPi / PipeWire / RASPIAUDIO 8×8
```

The current prototype uses a preallocated mmap file containing lock-free SPSC
rings and atomics; no file or socket operation occurs in the audio callback.
Migration to an authenticated launchd/Mach service and real PTP discipline is
still pending, so this checkpoint is not described as production-ready.
